# 렌더 지연과 프레임 지정 캡처

## 현상
0.5 m/s에서는 정확도 100%였는데, 1.5 m/s에서는 **30개 전부 unknown**(28건이 "no foreground in ROI")이 나왔다. 프레임을 보니 제품이 검사선보다 약 0.5m **상류**(아직 오는 중)에 찍혀 있었다. 이미지가 시뮬레이션 상태보다 늦은 것이다.

0.5 m/s에서 맞았던 것도 지연이 약 0.15m라 검사 창(±0.25m) 안에 겨우 들어갔기 때문이었다. **운 좋게 여유 안에 들어온 것**이지 옳은 설계가 아니었다.

## 측정 (`probe_capture.ps1`의 lag 측정)
`viewport_api.frame_info["swh_frame_number"]`(렌더된 stage 상태의 번호)와 `app.get_update_number()`를 비교했다.

| 설정 | 요청 시 update | 캡처된 프레임 swh | 지연 |
|---|---|---|---|
| 기본(비동기 렌더링) | 1682 | 1629 (update 1698에 도착) | **약 70 update** |
| `app.asyncRendering = false` | 529 | 525 (update 532에 도착) | 약 5 update |

- swh 번호는 update 번호를 그대로 따라간다(동기 렌더링에서 확인).
- Kit의 테스트용 앱들은 `--/app/asyncRendering=false`를 쓴다. 즉 기본값은 비동기다.

## 해결
1. **동기 렌더링:** 앱 설정 `app.asyncRendering = false`
2. **프레임 지정 캡처:** 검사선을 통과한 update의 번호를 `frame_to_capture`로 넘긴다.
   ```python
   target = omni.kit.app.get_app().get_update_number()   # 제품 프림을 검사선에 놓은 update
   cap = ByteCapture(cb, aov_name="LdrColor", frame_to_capture=target, viewport=viewport_api)
   viewport_api.schedule_capture(cap); await cap.wait_for_result()
   offset = cap.frame_info["swh_frame_number"] - target   # 0이어야 한다
   ```
   그러면 이미지가 **트리거 시점의 상태**를 정확히 보여 준다. 렌더 지연과 무관하다.
3. **검증:** `frame_offset != 0`이면 그 판정을 붙이지 않고 `unknown`으로 기록한다(`frame_mismatches`).
4. 이 방식으로 이전의 "새 프레임 1장 대기 + stale 재시도"를 대체했다. stale 감지는 안전장치로 남겼다.

## 부작용과 대응
- 동기 렌더링에서는 앱 전체가 렌더 속도(약 10 fps)로 돈다. 시뮬레이션을 **실시간 dt**로 돌리면 캡처 지연이 0.5~2.3초가 되고, 1.5 m/s에서 판정 5/30이 배출선에 늦게 도착했다(late → fail-safe).
- 그래서 시뮬레이션을 **고정 스텝(1/60 s/update)**으로 바꿨다 → [[2026-10-21 고정 시뮬레이션 스텝과 동기 렌더링]]
