# 면접 준비용 Omniverse 고도화 작업 계획

## 작업 상태와 범위

- 기준일: 2026-10-26. 포트폴리오는 기존 구현 기준으로 제출된 상태다.
- 상태: **2026-10-29 구현·계획한 실험·회귀 검증 완료**. 최종 결과 감사 `results/interview/verification.json`은 passed=true다. 실패한 최초 재개 배치와 native 이미지 내용 불일치의 미해결 원인은 보존한다. 실제 결과·적용 범위·한계는 [[2026-10-26 면접 준비용 Omniverse 고도화 구현]]에 기록했다.
- 작업 범위: 기존 프로젝트의 시간 정합, Kit 비동기 수명주기, USD 합성, 인스턴싱 비용을 구현·측정한다.
- 비전 모델 재학습, 검사 정확도 고도화, 다중 공정 스케줄러, 강화학습, 실제 장비 제어는 이번 작업에 넣지 않는다. [[2026-10-24 계획 마무리 - 비전 검사 제외]]의 범위를 유지한다.
- 기존 결과를 덮어쓰지 않는다. 실험 결과는 `results/interview/<주제>/<실행ID>/`에 새로 저장한다.
- 새 Obsidian 노트는 하위 폴더를 만들지 않고 `docs/`에 추가한다. 구현 시 핵심 개념별 `type: concept`, 실제 변경별 `type: request` 노트를 만들고 이 계획 및 관련 기존 노트와 연결한다.

## P0. 기준 실행 고정

### 절차

1. Git 커밋과 작업 트리 변경 여부, 실행 날짜, OS·GPU·드라이버·Kit 버전을 기록한다.
2. `box` 고정 카메라와 `crown` 다시점 셀을 각각 실행한다. 모델·자산 누락과 대체 이송 사용 여부를 함께 기록한다.
3. 제품 수, seed, 속도, 조명, `fixedDt`, 동기/비동기 렌더 설정, 메인·검사 뷰포트 해상도를 기록한다.
4. 기존 `check_run`과 반복 실행 비교로 정상 기준을 확보한다. 이미 정상인 기능이 이후 변경으로 달라지는지 비교할 수 있게 run 경로를 보관한다.

### 현재 사용 가능한 명령

아래 명령은 기존 스크립트다. `<실행경로>`는 각 명령이 출력한 실제 경로로 바꾼다. 동일 조건을 두 번 실행해 비교한다.

```powershell

.\scripts\collect_frames.ps1 -Seed 42 -Products 30 -Speed 0.5 -Part box
.\scripts\collect_frames.ps1 -Seed 42 -Products 30 -Speed 0.5 -Part crown
.\scripts\check_run.ps1 -RunDir <실행경로>
.\scripts\compare_runs.ps1 -RunA <첫번째실행경로> -RunB <두번째실행경로>
```

## P1. 시뮬레이션·렌더·캡처 시간 계측

### 시작 지점

- `source/extensions/visiontwin.factory/visiontwin/factory/extension.py`: `_on_update`, `_request_inspection`, `_request_view`, `_record`, `_apply_verdict`.
- `source/extensions/visiontwin.factory/visiontwin/factory/frame_provider.py`: `request_frame`, `_capture_async`, `TIMEOUT_UPDATES`.
- 기존 관측: [[렌더 지연과 프레임 지정 캡처]], [[프레임 지정 캡처에서 stale 오탐]], [[셀 카메라에서 프레임 번호가 맞아도 이전 화면이 오는 경우]].

### 구현 절차

1. run·요청별 식별자를 추가한다. 최소 식별자는 `run_id`, `generation`, `request_id`, `product_id`, `view`로 한다. 캡처와 판정의 모든 로그에 같은 식별자를 전달한다.
2. 같은 프로세스의 경과시간은 `time.perf_counter()`로 측정한다. UTC 시각은 실행 식별용으로 별도 기록하고 두 종류의 시간을 뺄셈하지 않는다.
3. 요청 시점의 시뮬레이션 시간·앱 update 번호와 완료 시점의 값을 각각 저장한다. 요청 시점 값을 콜백에서 현재 값으로 다시 읽어 대체하지 않는다.
4. 다음 이벤트를 `trace.csv`에 남긴다: `STATE_APPLIED`, `CAPTURE_REQUESTED`, `CAPTURE_RECEIVED`, `INSPECTION_DONE`, `VERDICT_APPLIED`, `TIMEOUT`, `CANCELLED`, `DISCARDED`.
5. 이미지 수신 시점과 이미지가 나타내는 상태를 구분한다. `CAPTURE_RECEIVED`를 실제 GPU 렌더 완료 시각이라고 표현하지 않는다. 요청·반환 프레임 번호와 이미지 내용 검증 결과를 별도 필드에 남긴다.
6. 업데이트 횟수 제한과 실제 경과시간 제한을 설정·종료 사유에서 구분한다. `TIMEOUT_UPDATES=180`을 실제 3초로 취급하지 않는다. 실제 시간 제한값은 기준 측정 후 정하고 run 설정에 저장한다.
7. 타임아웃·취소·중복 완료가 경쟁해도 요청은 한 번만 종료되게 한다. 이미 종료된 요청의 늦은 결과는 판정에 전달하지 않고 기록만 남긴다. 구현은 P2의 작업 관리와 통합한다.
8. 이벤트 루프가 진행되는 동안의 실제 시간 타임아웃과 프로세스 정지를 구분한다. Kit 자체가 멈춘 경우는 외부 실행기의 최대 대기시간으로 감지하고 별도 실패로 저장한다.

### 추적 필드와 집계

| 구분 | 필드·계산 |
|---|---|
| 요청 연결 | run, generation, request, product, view, 이벤트 종류 |
| 시뮬레이션 | 요청·완료 시 sim time, update 번호 |
| 캡처 | 요청·반환 SWH 프레임 번호, offset, 이미지 digest, 내용 검증 상태 |
| 실제 시간 | 각 이벤트의 단조 증가 시각과 요청 대비 경과 ms |
| 종료 상태 | 정상·타임아웃·취소·구세대 폐기·변환 오류와 상세 사유 |
| 실행 속도 | `RTF = 시뮬레이션 진행시간 / 실제 경과시간` |
| 지연 | 캡처·검사·최종 판정까지의 p50/p95/max, 최대 pending 수 |

초기 Stage 생성·셰이더 준비 시간과 정상 운전 구간을 나눠 기록한다. 실제 시간 처리량과 시뮬레이션 시간 기준 생산량도 구분한다. 시간 제한·취소된 요청 수를 지연 통계와 함께 표시한다.

### 실험 절차

1. 기준 설정에서 계측 자체가 판정·분류 결과를 바꾸지 않는지 확인한다.
2. 고정 seed·제품 수·속도로 메인 뷰포트 배율을 변경한다. 검사 카메라 해상도는 유지해 렌더 부하 효과를 먼저 분리한다.
3. 같은 조건에서 `fixedDt=1/60`과 기존 실제 경과시간 기반 설정을 비교한다. 동기/비동기 렌더 비교는 별도 실험으로 분리하고 지원 여부부터 확인한다.
4. 진단 전용 지연 주입으로 완료 지연·타임아웃·늦은 콜백을 재현한다. 메인 스레드에 `sleep`을 넣어 전체 업데이트를 멈추는 방식은 쓰지 않는다. 지연을 주입한 위치와 실제 GPU 지연 여부를 구분한다.
5. 진단 전용 Stage에서 update에 대응하는 시각 패턴을 렌더하고 반환 이미지에서 디코딩해 상태 대응을 확인한다. 패턴이 안정적으로 보이는 카메라·조명에서 기준 검증부터 한다. 디코딩 불가는 불일치와 별도 집계한다.
6. 진단 패턴은 생산 검사 이미지·모델 입력에 넣지 않는다. 이미지 동일 여부만으로 stale을 확정하지 않는다. `box`의 정상적인 동일 이미지와 셀의 의심 프레임 사례를 각각 확인한다.
7. 조건별 3회 반복하고 원시 로그와 집계표를 저장한다. 성능 비교에는 정상 운전 구간과 동일한 측정 창을 사용한다.

## P2. 비동기 작업과 Extension·Stage 수명주기

### 확인된 구조와 검증 가설

- `request_frame()`은 캡처 coroutine을 예약한다. `destroy()`는 뷰포트를 파괴한다.
- `reset()`은 run 상태를 초기화하고, 콜백은 현재 검사기·제품 추적기·로그에 접근한다.
- **가설:** 이전 실행의 결과가 Reset·Stage 변경 이후 도착하면 새 실행 상태나 파괴된 자원에 접근할 수 있다. 실제 발생 여부는 먼저 재현한다.

### 재현 절차

1. P1 식별자를 사용해 요청이 pending인 시점을 확실히 포착한다. 단순히 임의의 시간 후 Reset하지 않는다.
2. pending 중 `Reset → Start`, `Build Scene`, 외부 Stage 닫기·교체, Extension 비활성화·재활성화를 각각 실행한다.
3. 정상 완료 직전, 완료 지연, 타임아웃 직전 조건에서 반복한다. 외부 Stage 변경은 버튼 경로와 따로 검증한다.
4. 구세대 판정 적용, 새 run 로그 오염, 존재하지 않는 product 접근, 종료 후 UI 접근, 중복 이벤트, 남은 task를 기록한다.

### 구현 절차

1. run/Stage 무효화 시 generation을 **상태 초기화와 자원 해제보다 먼저** 증가시킨다. 요청 시 generation과 자원 소유자를 고정한다.
2. frame provider는 예약한 task·요청을 추적한다. 신규 요청 차단, task 취소, 완료 대기, 자원 해제를 명시적으로 관리한다.
3. 콜백은 정상 경로와 오류 경로 모두 generation·종료 상태를 검사한다. 구세대 결과는 현재 검사기·tracker·로그·UI에 접근하기 전에 폐기한다.
4. `on_shutdown`이 동기 훅이라는 조건을 고려한다. 우선 무효화·요청 차단·취소로 접근을 막고, await 가능한 정리는 별도 종료 경로로 구성한다. task 정리 전 파괴된 뷰포트를 다시 참조하지 않도록 한다.
5. 캡처 요청 종료는 한 번만 처리하고 pending 카운터를 정리한다. waiter만 취소된 경우 실제 예약된 캡처 콜백이 이후 호출될 수 있는지도 검증한다.
6. Stage 이벤트를 구독해 외부 닫기·교체도 같은 무효화 경로로 보낸다. 구독은 Extension 종료 시 해제한다.
7. 초기화·Build Scene·Start의 중복 실행과 setup coroutine 재진입을 제어한다. 자원이 준비된 generation에서만 실행을 시작한다.
8. Reset 시 기존 로그의 종료·미완료 상태를 기록하고 파일 핸들을 정리한다. 중단 run을 정상 완료 run으로 집계하지 않는다.

## P3. USD 변환과 레이어 합성 최소 예제

### 시작 지점

- `scene_manager.py`: `spawn_product_prim`, `set_product_pose`.
- `scripts/make_part_variants.py`: `build_layer`.
- 기존 사례: [[USD 참조와 xformOp 충돌 (부품이 벨트에 묻힘)]].

### 구현 절차

1. 중심 보정·회전·스케일을 가진 작은 자산 USD를 만든다. 기준 로컬/월드 행렬과 bbox를 계산한다. meter/mm 단위 사례를 준비하고, up-axis 변경은 실제 좌표 변환과 메타데이터 변경을 구분한다.
2. A: 참조한 prim에 같은 이름의 translate opinion을 작성한다. B: 배치용 부모 Xform 아래에서 참조한다. 같은 입력으로 최종 행렬·bbox·`xformOpOrder`를 비교한다.
3. 자산, 배치, 실행 상태용 레이어를 구성한다. sublayer 순서와 각 레이어의 책임을 명시하고 `Usd.EditContext` 등으로 편집 대상을 지정한다.
4. 같은 속성에 다른 값을 작성해 최종 값과 작성 출처를 확인한다. property stack·resolve 정보·레이어 강도를 덤프해 어떤 값이 선택되는지 수치로 검증한다.
5. 실행 상태 레이어만 비우거나 구성에서 제외해 배치는 유지하고 원본 상태가 복원되는지 확인한다. 저장·재열기 후에도 배치와 참조가 유지되는지 확인한다.
6. 별도 파생 파일 방식과 USD VariantSet 방식으로 동일한 두 상태를 만든다. 선택 저장, 참조 공유, 재질 변경, 파일 관리 차이를 표로 비교한다. 현재 파일 이름의 variant를 VariantSet 구현으로 표현하지 않는다.
7. 원본 USD의 해시가 바뀌지 않는지 확인한다. 깨진 참조나 prim 경로 변경은 오류로 보고한다. 원본 갱신이 모든 오버라이드에 자동 대응한다고 가정하지 않는다.

- [x] 편집 대상과 최종 속성값의 관계를 파일에서 추적할 수 있다.
- [x] 실행 상태 제거·저장·재열기 후 배치 유지와 원본 해시 불변을 확인했다.

## P4. 인스턴싱 유지·해제와 반복 배치 비용

### 시작 지점

`scripts/make_part_variants.py`의 `paint_targets()`는 개별 메시의 재질 바인딩을 작성하기 위해 인스턴싱을 해제한다. 이 선택의 편집 가능 범위와 반복 배치 비용을 비교한다. LOD 조건은 [[HOOPS 변환 옵션 실측 (LOD, 문자열 인자, 물리량)]]과 연결한다.

### 구현 절차

1. 같은 원본 형상·재질·카메라로 A: 일반 Reference, B: instanceable Reference, C: B에서 개별 편집을 위해 인스턴싱 해제한 구성을 만든다.
2. 구조 비용 비교는 셋의 외형을 동일하게 유지한다. 특정 자산 하나의 재질만 바꾸는 기능 검증은 별도 수행한다.
3. 공유 형상은 내부에 두고 개별 이동은 인스턴스 루트 또는 부모 Xform에 작성한다. instance proxy 내부 속성 편집 제한과 대체 편집 방법을 확인한다.
4. 반복 개수는 10→50→100 순으로 늘리되 각 단계에서 메모리와 안정성을 확인한다. 장비 한계를 넘기기 위해 무리하게 계속 늘리지 않고 중단 조건과 실제 완료 개수를 기록한다.
5. 매 구성은 별도 프로세스로 실행한다. 동일 해상도·조명·렌더 설정·warm-up·측정 update 수를 사용한다. 첫 로드와 캐시가 준비된 로드를 구분한다.
6. Stage open과 첫 유효 렌더까지 시간을 따로 측정한다. 프로세스 메모리, 측정 도구가 제공하는 GPU 메모리, 정상 운전 프레임 시간 p50/p95, instance/prototype 수를 기록한다. GPU 전체 사용량만 얻는 경우 프로세스 전용 사용량으로 표시하지 않는다.
7. 조건별 3회 반복한다. LOD 비교는 인스턴싱 비교를 마친 뒤 다른 변수는 고정하고 수행한다. 품질 측정은 기존 LOD 리포트를 재사용한다.
8. 결과를 근거로 정적 공유 형상·관절 이동 계층·개별 재질 편집 범위를 정한다. 이점이 확인되지 않으면 결과를 그대로 남기고 운영 코드 적용을 강제하지 않는다.

## P5. 회귀 확인과 결과 정리

1. 변경과 관련된 순수 Python·USD 검증, Kit 통합 테스트를 실행한다. 변경하지 않은 영역의 반복 테스트는 새 실패나 우려가 있을 때 추가한다.
2. P0의 `box`/`crown` 조건을 다시 실행하고 제품 ID별 판정·경로·시뮬레이션 결과를 비교한다. 의도한 타임아웃·취소 정책 변경은 사유를 명시한다.
3. 진단 기능을 껐을 때 기존 run 형식과 분석·감사 스크립트가 계속 동작하는지 확인한다. 새 필드는 기존 소비자와의 호환성을 확인한다.
4. 각 실험 결과를 `재현 명령 → 입력 조건 → 관측 → 코드 변경 → 재검증 → 남은 한계` 순서로 정리한다.
5. 새 스크립트마다 목적·입력·출력·환경·실패 종료 코드를 적고 실제 실행한 명령을 남긴다. 미구현 명령은 계획으로 표시한다.
6. 각 주제에서 코드 한 곳, 원시 로그 한 곳, 결과표 한 곳을 바로 찾을 수 있게 연결한다. 구현 변경 노트와 개념 노트를 이 계획 및 `[[index]]`에 연결한다.
