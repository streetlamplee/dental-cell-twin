# README 부분별 데모 클립

사용자 요청: 부분마다 클립을 따로 녹화하고, README에서 부분마다 자세히 설명한다.

## 만든 것
- `scripts/record_clips.ps1` + `record_clips.py`: run 하나(seed 42)에서 **크라운 #3(치핑 불량) 하나를 따라가며** 클립 6개를 녹화한다.
  - 한 제품의 구간들은 시간이 겹치지 않는다(진입 → 로딩 → 검사 → 언로딩 → 배출). 그래서 run 한 번에 모든 클립을 찍을 수 있다.
  - 클립 사이 구간은 캡처하지 않는다.
  - 티칭 펜던트는 열면 라인을 멈춘다. 그래서 배출 클립이 끝나자마자 연다(라인이 끝날 때까지 기다리지 않는다).

| 클립 | 화면 | 길이 |
|---|---|---|
| 01_line | 넓은 화면 + 크라운 표시 원 | 2.9 s |
| 02_load | 셀 근접 | 2.2 s |
| 03_inspect | 스핀들 카메라 + 검사기가 저장한 프레임(가운데 확대)과 시점 판정 | 3.5 s |
| 04_unload | 셀 근접 | 2.2 s |
| 05_reject | 넓은 화면(벨트, 푸셔, bin) + 크라운 표시 원 | 2.3 s |
| 06_teach | 티칭 근접 | 9.0 s |

- 출력:
  - MP4: `results/demo/clips_<timestamp>/` (git 제외)
  - GIF: `docs/screenshots/clips/`. 560 px, 10 fps, 합계 약 5 MB
- README에 "데모 클립: 크라운 #3 하나를 따라가며" 절을 추가했다. 클립마다 세 가지를 쓴다:
  - 보이는 것
  - 어떻게 동작하나 (코드 위치, 방법, 막혔던 점)
  - 실측 수치 (#3 시점별 판정 표, 셀 사이클, 티칭 결과). 기존 측정 절로 링크한다
- 녹화 run `20261024_142845_seed42`: 4개 모두 분류 정확, #3 판정 defect(shape)
  - 판정을 정한 시점은 side_a다. 실루엣 0.081, 외곽선 0.040

## 녹화하면서 고친 것 (테이크 6번)
1. **크라운이 너무 작다:** 실제 크기 크라운은 약 1 cm다. 라인 전체가 보이는 고정 카메라에서는 몇 픽셀이었다. 세 방법을 시도했다:
   - 크라운을 따라 움직이는 카메라: 무늬 없는 벨트만 보여서 움직임이 안 보였다. 배출 때는 카메라가 푸셔와 bin을 뚫고 지나갔다.
   - 고정 위치에서 크라운 쪽으로만 도는 카메라: 여전히 주변 맥락이 없었다.
   - **최종:** 넓은 고정 화면에 노란 원을 그린다. 원의 위치는 크라운 USD 프림 위치를 녹화 카메라의 행렬로 투영한 값이다.
     - Kit는 수평 조리개를 화면 폭에 맞춘다. 그래서 초점거리를 픽셀로 바꿀 때 `focal / h_aperture × W`를 쓴다.
2. **원이 크라운보다 앞서 간다:** 캡처 이미지가 요청 시점보다 3업데이트 전의 장면이었다 → [[뷰포트 캡처 이미지는 요청보다 3업데이트 늦다]]. 3업데이트 전 위치로 원을 그려 맞췄다.
3. **배출 카메라에 bin이 잘렸다:** 크라운이 bin으로 떨어지는 방향은 카메라에서 약 46° 아래다. 24 mm 렌즈의 세로 반화각(13.8°)으로는 담을 수 없었다. 카메라를 뒤로, 위로 옮기고 bin 쪽을 겨눴다.
4. **검사 프레임 창 속 크라운이 작다:** 640×480 검사 프레임에서 크라운은 가운데 일부만 차지한다. 가운데 36 %만 잘라 확대했다.
5. **티칭 클립 첫 프레임이 이전 카메라 화면이다:** 펜던트가 카메라를 바꾼 직후 4업데이트로는 부족했다. `next_viewport_frame_async(vp, 10)`으로 기다린다.
6. **시점별 값의 흔들림:** 같은 seed로 다시 돌리면, 정상 시점의 실루엣 차이는 0.001~0.002 달라진다. 클립 run 6번에서 side_a는 모두 실루엣 0.081, 외곽선 0.040~0.041로 defect였다. README 표는 클립을 녹화한 run의 값을 쓰고, 이 흔들림을 적었다.
