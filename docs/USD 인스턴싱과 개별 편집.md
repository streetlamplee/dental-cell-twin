# USD 인스턴싱과 개별 편집

- 일반 참조, instanceable 참조, 인스턴싱 해제 구성을 같은 원본·외형으로 비교한다.
- 공유 구조 내부의 instance proxy를 직접 편집하는 제약과, 한 개만 해제한 뒤 나머지 공유를 유지하는 동작을 검증한다.
- 개별 배치는 루트·부모 Xform에서 관리하고, 공유 형상과 개별 편집의 경계를 정한다.
- USD open 시간·프로세스 RSS와 Kit 첫 프레임·정상 운전 update 간격은 서로 다른 지표다. Kit update 간격을 GPU 단독 렌더 시간으로 표시하지 않는다.
- `nvidia-smi`의 장치 전체 메모리는 프로세스 전용 VRAM이 아니다. 새 프로세스 실행 역시 OS·드라이버 캐시가 비워졌음을 뜻하지 않는다.
- 인스턴싱의 성능 이득은 사전 가정하지 않고 반복 측정 결과로 기록한다.

실험 진입점은 `scripts/benchmark_usd_instancing.ps1`, `scripts/benchmark_interview_render.ps1`이다.

## 현재 적용 범위

실제 crown 자산의 10/50/100개 배치에서 일반 참조·인스턴스·인스턴싱 해제를 각각 3회 비교했다. 100개 구성의 USD 프로세스 RSS 중앙값은 일반 참조 약 67.4 MiB, 인스턴스 약 65.6 MiB였고, Kit update p50은 둘 다 약 10.2 ms였다. 이번 측정으로 뚜렷한 렌더 속도 개선을 주장하지 않는다.

공유 형상의 루트 배치는 인스턴싱을 유지한 채 수정할 수 있지만, instance proxy 내부의 개별 메시 재질 바인딩은 직접 수정할 수 없었다. 한 개를 인스턴싱 해제해 재질을 바꾸고 다른 인스턴스의 공유가 유지되는 것을 별도 검증했다. 따라서 운영의 개별 결함·재질 편집 흐름은 유지하고, 공유 가능 범위와 비용 비교는 실험 Stage에 둔다.

원시 표와 렌더 결과는 `results/interview/instancing/20261026_230542/`에 있다. LOD 비교는 [[HOOPS 변환 옵션 실측 (LOD, 문자열 인자, 물리량)]]의 형상 오차 표와 함께 읽고, 실제 렌더 결과가 확보된 뒤 판단한다.

## LOD 50개 배치 실측

`results/interview/lod/20261029_211444/`에서 50개 인스턴스·960×640·60 update warm-up·120 update 측정을 LOD별 새 Kit 프로세스로 3회 수행했다. 표의 update p50/p95는 세 실행의 update 표본을 합쳐 계산했고, 메모리는 실행별 RSS 중앙값이다. 형상 수치와 오차는 기존 CAD 변환 리포트를 재사용했다.

| LOD | 원본 삼각형 수 | 기존 체적 오차 | Kit update p50 / p95 | Kit RSS |
|---|---:|---:|---:|---:|
| 0 | 608 | -1.680% | 10.17 / 11.19 ms | 5556.8 MiB |
| 3 | 16,774 | -0.052% | 10.29 / 11.37 ms | 5546.3 MiB |
| 4 | 30,700 | -0.031% | 10.31 / 12.42 ms | 5567.3 MiB |

이 크기의 배치에서는 낮은 LOD로 일관된 메모리 절감이나 큰 update 속도 향상을 입증하지 못했다. 현재 자산을 일괄 저해상도로 바꾸지 않는다. 정밀 형상·물리량이 필요한 자산은 기존 정밀도를 유지하고, 더 큰 배치나 확대 시각 품질을 따로 검증한 뒤 LOD를 선택한다. 체적·면적 오차와 원거리 화면의 유사성을 검사 정확도 보장의 근거로 쓰지 않는다.
